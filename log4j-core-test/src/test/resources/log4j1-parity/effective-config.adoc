= Log4j 1.x to Log4j 2 configuration parity corpus (`log4j-core-test`)

This directory is the behaviour-preservation oracle for the Log4j 1.x configuration fixtures that
were translated in place into the Log4j 2 schema inside `log4j-core-test/src/test/resources`.

Each translated fixture contributes two things:

* a *normalized baseline capture* -- `<fixture>.baseline.txt` -- recording exactly what the Log4j 1.x
  configuration rendered before the migration, and
* an *effective-configuration table* in this document, whose Log4j 2 column is populated from
  status-logger output observed while booting the translated file with `-Dlog4j2.debug`, never from
  reading the translated XML.

Acceptance for every fixture is an *empty* normalized diff between its baseline capture and the
output the migrated configuration renders for the same event script. A non-empty diff is a defect in
the migration; it is never resolved by widening the normalizer or by editing a baseline.

== Normalization

Exactly four tokens are normalized, and nothing else:

[cols="1,1,3",options="header"]
|===
| Rendered element | Normalized to | Why

| `%d` timestamp
| `<TS>`
| Wall-clock, non-deterministic.

| `%t` thread name
| `<THREAD>`
| Pool-assigned, non-deterministic.

| `%L` source line number
| `<LINE>`
| A source-layout artefact of the migration itself. Class and method names are *not* normalized.
  No fixture in this directory uses `%L`, so for this module the rule never fires.

| Absolute filesystem paths
| `<PATH>`
| Workspace-dependent.
|===

Everything outside those four tokens is compared byte for byte: level text *and its padding width*,
logger-name abbreviation, every literal separator, context-map placeholder rendering, and throwable
rendering.

=== Rule 6 arbitration -- should `bufferedIo` also be stated explicitly?

Decision:: *No.* `bufferedIo` is deliberately omitted from the translated fixture.

The Log4j 1.x source declares no `BufferedIO` parameter, so there is no value to carry across; the
open question was whether to state Log4j 1.x's *default* of `false` explicitly in order to reproduce
the bridge's observed disposition. Baseline observed output is the tie-breaker, and it resolves the
question as follows.

. *The rendered output is already identical.* The normalized diff between `log4j12-perf.baseline.txt`
  and the output of the migrated fixture is empty, and it reproduces across independent capture
  rounds. Buffering governs only *when* bytes reach the disk, never *what* is written, so the
  tie-breaker's own trigger for revisiting this question -- a non-empty diff attributable to
  buffering -- does not fire.
. *Omission reproduces genuine Log4j 1.x, whereas the explicit value reproduces a bridge artefact.*
  Log4j 1.x's `FileAppender` always writes through a `java.io.OutputStreamWriter`, whose encoder
  holds an 8192-byte buffer, and adds a `BufferedWriter` on top of it only when `BufferedIO` is
  true; it flushes per event only when `ImmediateFlush` is true. With `BufferedIO=false` and
  `ImmediateFlush=false`, therefore, Log4j 1.x still buffers roughly 8 KiB and does not flush per
  event. Log4j 2's `bufferedIo` does not mean the same thing: it controls whether there is any byte
  buffer at all. Leaving it unset yields `bufferedIo=true` with `bufferSize=8192`, which is
  precisely the Log4j 1.x disposition. Stating `bufferedIo="false"` instead reproduces the bridge's
  behaviour of writing every event straight through -- something Log4j 1.x never did -- and also
  reproduces the bridge's warning, because the bridge forwards `bufferSize=8192` alongside
  `bufferedIo=false`.
. *A control run confirms both halves of point 2.* Adding `bufferedIo="false"` to the translated
  fixture makes the first event's bytes appear on disk before shutdown and raises
  `WARN The bufferSize is set to 8192 but bufferedIo is false: false`, exactly as the bridge does.
  With the attribute omitted, nothing is on disk until the appender stops, and no warning is raised.
  Note that this is Log4j 2's `bufferSize`-versus-`bufferedIo` warning; the separate
  "Locking and buffering are mutually exclusive" warning requires `locking="true"` and is not
  involved here.

The migrated fixture therefore emits strictly fewer diagnostics than the baseline and introduces no
new warning, while matching Log4j 1.x's buffering and flushing behaviour rather than the bridge's
approximation of it.

=== Pattern token audit

The bridge does not hand a Log4j 1.x conversion pattern to Log4j 2 verbatim: it rewrites `%p` to
`%v1Level`, `%x` to `%ndc` and `%X` to `%properties`, then delegates to Log4j 2's own
`PatternLayout`. Every token in this fixture that is neither `%p` nor `%X` is consequently already
being rendered by the very same Log4j 2 converter that the translated fixture uses, so `%d`, `%t`,
`%c{1}`, `%m` and `%n` are identical by construction. Padding and precision are preserved for the
same reason, the rewrite re-emitting the captured width: `%5p` becomes `%5v1Level`.

The two tokens whose converter identity does change are equivalent here, and the baseline capture
demonstrates it rather than merely asserting it:

[cols="1,3",options="header"]
|===
| Token | Evidence from the baseline capture

| `%5p`
| The bridge converter renders a level converted by *name*, the native converter renders the level
  itself; for standard levels these agree. The capture shows `DEBUG`, `ERROR` and `FATAL` unpadded
  and `INFO` and `WARN` padded to width five, identically in both worlds. This fixture declares no
  custom level, which is the only case in which the two could diverge.

| `%X{transactionId}`
| Both the bridge converter and the native converter take a single-key branch that appends the value
  when present and appends nothing when absent. The capture exercises both: with the key populated
  the line reads `... PerformanceComparison TX-0001 - ...`, and with the key absent it reads
  `... PerformanceComparison  - ...` -- a *double space* before the separator, because the key
  resolves to the empty string. That double space is correct, byte-identical behaviour and must not
  be "tidied" away, either in the pattern or in the baseline.
|===

`%c{1}` retains one name element counted from the end, so the capture shows the full simple logger
name -- `PerformanceComparison`, `FileAppenderProbe`, `child` -- and never a dot-abbreviated form.
No `%x`, bare `%X`, `%properties`, `%v1Level`, `%r`, `%C`, `%M` or `%L` token appears in this
fixture, and none was introduced.

=== Rolling policies

None apply. The fixture uses a plain Log4j 1.x `FileAppender` and declares no
`DailyRollingFileAppender`, no Log4j 1.x `RollingFileAppender`, and no `MaxFileSize`,
`MaxBackupIndex` or `DatePattern` option. No rolling appender, triggering policy or rollover
strategy was introduced.

=== Event script behind the baseline capture

The capture was produced by replaying a fixed script whose constants were shared by both worlds, so
that any difference in rendered output would be attributable to the configuration translation alone:
one event below the root threshold, which both worlds suppress; one event at each of `DEBUG`, `INFO`,
`WARN`, `ERROR` and `FATAL` on `org.apache.logging.log4j.PerformanceComparison`, the logger name the
consuming comparison test shares across all three logging generations; one event on a second,
differently shaped logger name so that name abbreviation is exercised; one event with the
`transactionId` key populated and one with it removed; one event from a child logger, which additive
propagation must deliver to the root appender exactly once; and one event carrying a throwable whose
stack trace is pinned to fixed frames so that throwable rendering is compared without needing any
further normalization.

The harness that drove the Log4j 1.x side is transient and is not committed: it necessarily used the
`org.apache.log4j` facade, and no committed source file in this repository outside the
`log4j-1.2-api` module may reference that package. Only the normalized capture is committed.

=== Rule 6 arbitration -- the queue-full policy, `blocking`

Decision:: *State `blocking="true"` explicitly,* even though the bridge is observed to build the
asynchronous appender with `blocking=false`.

This is the one place in this translation where a stated value deliberately departs from the bridge's
*observed* value, so the evidence is set out in full.

. *The bridge's `false` is an artefact of the bridge, not Log4j 1.x behaviour.* The bridge's
  asynchronous-appender builder holds its blocking flag in a freshly created boolean holder and
  overwrites it only when the source declares a `Blocking` parameter. This fixture declares none, so
  the holder's own `false` is forwarded. Genuine Log4j 1.x does the opposite: disassembling the
  published Log4j 1.2.17 artefact shows its asynchronous appender's no-argument constructor storing
  `1` -- true -- into its `blocking` field, alongside `128` for the buffer size and `0` for location
  capture. Log4j 1.x therefore applies back-pressure by default, and `blocking="true"` reproduces
  Log4j 1.x while `blocking="false"` would reproduce the bridge's approximation of it.
. *The flag cannot affect rendered output, so the baseline cannot arbitrate against it.* Blocking
  governs only what happens when the queue is *full* -- wait for space, or discard. The queue holds
  262144 events and the script emits eleven, so the full path is never taken. A control run of the
  translated fixture with `blocking="false"` produces a normalized capture byte-identical to the
  committed baseline, which demonstrates directly that this attribute is invisible to the comparison.
. *Preserving back-pressure is the conservative choice for a benchmark fixture.* These fixtures serve
  a measurement instrument. Silently switching a saturated queue from waiting to discarding would
  change both what is measured and what is logged, and discarding events would breach the requirement
  that nothing be added, removed or re-levelled. Stating the attribute rather than relying on the
  Log4j 2 default also makes the decision visible to a reviewer, which is why it is the single
  default this translation restates.

=== Rule 6 arbitration -- root additivity

Decision:: *Add no `additivity` attribute,* even though the root object's observed flag differs
between the two worlds.

. *The difference is confined to an inert field.* Additivity controls whether a logger's events are
  also passed to its *parent*. The root has no parent, so its own flag can propagate nothing. What
  additivity has to preserve here is that a *child* logger's event still reaches the root's appender
  exactly once, and the committed baseline exercises exactly that: the script's child-logger event
  appears once in the Log4j 1.x capture and once in the Log4j 2 capture, in the same position.
. *The observed values reflect two different construction paths, not two different intents.* The
  bridge mutates the configuration's pre-existing default root object, which carries `additive=true`;
  Log4j 2's `<Root>` plugin builder constructs a fresh root logger whose unset `additivity` attribute
  falls to the builder's `false`. That is how *every* Log4j 2 `<Root level="..."/>` element in this
  repository behaves; it is not a property of this translation.
. *A control run confirms the field is inert.* Adding `additivity="true"` to the translated fixture
  makes the probe report `additive=true`, matching the Log4j 1.x observation exactly -- and leaves the
  normalized capture byte-identical to the committed baseline. Since the attribute buys no
  behavioural change, it is omitted, keeping the translated fixture free of anything the Log4j 1.x
  source did not state.

=== Pattern token audit

The bridge does not hand a Log4j 1.x conversion pattern to Log4j 2 verbatim: it rewrites `%p` to
`%v1Level`, `%x` to `%ndc` and `%X` to `%properties`, then delegates to Log4j 2's own
`PatternLayout`. The probe makes that visible -- the Log4j 1.x arm's effective pattern is observed as
`%d %v1Level %c{1} [%t] %properties{aKey} %m %n` while the translated fixture's is observed as
`%d %p %c{1} [%t] %X{aKey} %m %n`. Every token that is neither `%p` nor `%X` is consequently already
being rendered by the very same Log4j 2 converter the translated fixture uses, so `%d`, `%c{1}`,
`%t`, `%m` and `%n` are identical by construction.

The two tokens whose converter identity does change are equivalent here, and the baseline capture
demonstrates it rather than merely asserting it:

[cols="1,3",options="header"]
|===
| Token | Evidence from the baseline capture

| `%p`
| Unpadded, unlike the width-five form used elsewhere in this directory, so no padding is involved.
  The bridge converter renders a level converted by *name* and the native converter renders the level
  itself; for standard levels these agree. The capture exercises all five that the root threshold
  admits -- `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL` -- and every one renders identically in both
  worlds. This fixture declares no custom level, which is the only case in which the two could
  diverge; other fixtures in this directory do declare custom levels, so the claim is scoped to this
  fixture rather than to the module.

| `%X{aKey}`
| Both the bridge converter and the native converter take a single-key branch that appends the value
  when present and appends nothing when absent. The capture exercises both: with the key populated
  the line reads `... [<THREAD>] async-parity event emitted while ...`, and with it removed the line
  reads `... [<THREAD>]  event emitted after ...` -- a *double space*, because the key resolves to the
  empty string. Log4j 2's whole-map and multiple-key branches would instead have rendered `{}` on
  empty data, which is precisely why the single-key form matters. That double space is correct,
  byte-identical behaviour and must not be "tidied" away, in the pattern or in the baseline.
|===

`%c{1}` retains one name element counted from the end, so the capture shows the full simple logger
name -- `RunLog4j1`, `AsyncAppenderProbe`, `child` -- and never a dot-abbreviated form. The pattern
ends `%m %n`, with a real space, so every rendered line carries a *significant trailing space* before
the line separator; it is preserved in the fixture and in the baseline, and must not be trimmed. No
`%x`, bare `%X`, `%properties`, `%v1Level`, `%r`, `%C`, `%M` or `%L` token appears in this fixture,
and none was introduced. Because the pattern names no explicit throwable specifier, a plain throwable
converter is appended implicitly -- identically in both worlds, since both delegate to the same
`PatternLayout` -- so the throwable renders after the line separator with no jar-and-version suffixes,
and is compared byte for byte.

that any difference in rendered output would be attributable to the configuration translation alone:
one `TRACE` event below the root threshold, which both worlds suppress; one event at each of `DEBUG`,
`INFO`, `WARN`, `ERROR` and `FATAL` on
`org.apache.logging.log4j.core.async.perftest.RunLog4j1`, the logger name the selecting consumer
acquires, with the `INFO` message taken verbatim from that consumer's own latency-message constant;
one event on a second, differently shaped logger name so that name abbreviation is exercised; one
event with the `aKey` key populated and one with it removed; one event from a child logger, which
additive propagation must deliver to the root appender exactly once; and one event carrying a
throwable whose stack trace is pinned to fixed frames so that throwable rendering is compared without
needing any further normalization.

Two capture disciplines were mandatory for this fixture specifically, because it is asynchronous
*and* does not flush per event. First, its destination is shared with the synchronous fixture beside
it, so the destination file is deleted immediately before each boot and the two are never booted
concurrently. Second, when the last emission returns, events may still be queued and rendered bytes
may still be sitting in the encoder buffer, so each capture stops the logger context before reading
the file -- which drains the queue into the file appender and then flushes it. Waiting on a timer
instead would make the capture a race rather than a result, and relaxing the flush setting or
shrinking the queue to make output appear sooner would corrupt the very disposition being preserved.

The harness that drove the Log4j 1.x side is transient and is not committed: it necessarily used the
`org.apache.log4j` facade, and no committed source file in this repository outside the
`log4j-1.2-api` module may reference that package. Only the normalized capture is committed. Both
arms were replayed four times; all eight normalized captures are byte-identical, so the empty diff is
reproducible rather than incidental.
