= Log4j 1.x to Log4j 2 configuration parity corpus: effective configuration (T8-T10)

This directory is the behaviour-preservation oracle for the three Log4j 1.x configuration fixtures
that were translated in place into the Log4j 2 schema inside `log4j-core-test/src/test/resources`.

It exists to turn "behaviour preserved" from a claim into something a reviewer can check. Each
translated fixture contributes two artefacts:

* a *normalized baseline capture* -- `<fixture>.baseline.txt` -- recording exactly what the Log4j 1.x
  configuration rendered before the migration, and
* an *effective-configuration table* in this document, whose Log4j 2 column is populated from what
  was observed while booting the translated file with `-Dlog4j2.debug`, never from reading the
  translated XML.

*Acceptance for every fixture is an empty normalized diff* between its baseline capture and the
output the migrated configuration renders for the same event. A non-empty diff is a defect in the
migration. It is never resolved by widening the normalizer, and never by editing a baseline.

Seven further fixtures were translated in the same change, but they live in `log4j-perf-test` and are
documented by that module's own parity corpus. They are deliberately not covered, cross-referenced or
summarised here: each corpus documents the fixtures its own module owns, so that each document can be
verified against resources sitting beside it.

== How both columns were observed

The method is prescribed, not merely the goal:

[quote]
____
each translated configuration file is to be booted with `-Dlog4j2.debug`, and its effective logger
levels, additivity, and appender wiring compared against a documented table derived from the 1.x
original.
____

Accordingly, *the Log4j 2 column is populated from observed boot output and from interrogating the
objects the running configuration actually built.* Reading the translated XML and transcribing its
attributes is exactly what this directive forbids, and it is not what was done. `log4j2.debug` is a
real, supported property, declared in
`log4j-api/src/main/java/org/apache/logging/log4j/status/StatusLogger.java`; when it is set, status
level filtering is bypassed so that every status event reaches listeners. The constant holding its
name is `private`, so it is set as a JVM system property (`-Dlog4j2.debug`) and never referenced
programmatically.

Three independent observation arms were run, each booting a fixture, replaying the event script,
stopping the logger context and reading back the rendered file:

[cols="1,3,3",options="header"]
|===
| Arm | What it ran | What it establishes

| *Genuine Log4j 1.x*
| The unmodified 1.x fixture under the real `log4j:log4j:1.2.17` artefact, with no bridge and no
  Log4j 2 on the classpath, selected with `-Dlog4j.configuration`
| The authoritative *Observed, Log4j 1.x* column. This is what "the 1.x original" means: the library
  the fixtures were written against

| *Bridge*
| The same unmodified 1.x fixture through the `log4j-1.2-api` compatibility bridge, selected with
  `-Dlog4j.configuration` plus the experimental compatibility flag
| The path these fixtures actually took at the base commit. Used only to corroborate, and to expose
  two places where the bridge is an *approximation* of Log4j 1.x rather than a reproduction of it

| *Log4j 2*
| The translated fixture in an isolated `LoggerContext`, with only `log4j-api` and `log4j-core` on
  the classpath
| The *Observed, Log4j 2* column, and the rendered output that is diffed against the baseline
|===

*A row is accepted only when the Log4j 1.x-observed and Log4j 2-observed values agree.* Exactly one
row in this corpus does not agree on its raw value -- root additivity -- and it is not waved through:
it is reported as observed, shown to be behaviourally inert, and arbitrated in Record 4 against the
baseline. Additivity is *asserted from observation* in all three tables rather than assumed from a
documented default.

The harness that drove the two Log4j 1.x arms is transient and *is not committed*. It necessarily
used the `org.apache.log4j` facade, and no committed source file in this repository outside the
`log4j-1.2-api` module may reference that package. Only the normalized captures are committed. This
document is the sole file in this directory that names the Log4j 1.x namespace at all, and it does so
only in prose and in citations of evidence paths -- it is documentation, not code, and it resolves
nothing.

== Normalization

Exactly four tokens are normalized, and nothing else:

[cols="2,1,4",options="header"]
|===
| Rendered element | Normalized to | Why

| `%d` timestamp
| `<TS>`
| Wall-clock, non-deterministic.

| `%t` thread name
| `<THREAD>`
| Pool-assigned and harness-dependent, non-deterministic.

| `%L` source line number
| `<LINE>`
| A source-layout artefact of the migration itself, which shifts whenever lines above an emission are
  edited. *Inert in this corpus:* none of T8, T9 or T10 uses `%C`, `%M` or `%L`, so the rule never
  fires here. It is retained so that this module's normalizer stays byte-identical to the sibling
  module's. *Class and method names are never normalized* -- only the line number would have been.

| Absolute filesystem paths
| `<PATH>`
| Workspace-dependent.
|===

Everything outside those four tokens is compared byte for byte: level text *and its padding width*,
logger-name abbreviation, every literal separator, context-map placeholder rendering, and throwable
rendering.

Two whitespace consequences are load-bearing and are called out here because they look like
formatting noise and are not:

* T8's baseline contains a *double space immediately before the `-` separator*.
* T9's and T10's baselines contain a *double space* after `]` and a *significant trailing space*
  before the line separator.

Both fall out of correct, byte-identical behaviour, and both are explained in Record 3. Trimming,
right-stripping or collapsing whitespace in a baseline is a defect. `grep -nP '[ \t]$'` is *expected*
to match the T9 and T10 baselines.

== Capture ordering and capture hygiene

The baselines were captured *before the migration landed*, which is the only order in which they can
arbitrate anything:

[cols="1,3",options="header"]
|===
| Condition | Value

| Base commit
| `df1d9a5198c55339cc4eebe78030f4fbdf4d5070`, branch `2.x`

| JDK
| 17, per `.java-version`

| Maven
| 3.9.16, per `.mvn/wrapper/maven-wrapper.properties`

| Classpath state
| The Log4j 1.x classpath was still present; no dependency had been removed and no fixture had been
  translated

| Committed artefacts
| The normalized captures only. The capture harness is not committed
|===

Three disciplines were mandatory during capture, and remain mandatory for anything that reproduces
it:

. *T9 and T10 share a destination.* Both write the bare relative path `perftest.log`. They are never
  booted concurrently, and the destination is deleted immediately before each boot. Only T8 writes
  `target/testlog4j.log`, and it is deleted before its own boot for the same reason.
. *The context is stopped before the file is read.* T10 is asynchronous, and T9 and T10 both carry
  `immediateFlush="false"`, so when the last emission returns events may still be queued and rendered
  bytes may still be sitting in the encoder buffer. Stopping the context drains the queue into the
  file appender and then flushes it, which makes the read a result rather than a race.
. *Nothing is tuned to make output appear.* These fixtures serve a benchmark harness -- a measurement
  instrument. Waiting on a timer instead of stopping the context, relaxing `immediateFlush`,
  shrinking `bufferSize`, or replacing the asynchronous appender with a synchronous one would each
  make output appear sooner while destroying the very disposition being preserved. None was done, and
  none may be done.

== The event script, and where it lives

Each fixture is exercised by one event, chosen so that the emission is the one its real consumer
makes. The logger names, levels and messages are carried across character for character; logger names
in particular are never "improved".

One case makes that rule load-bearing rather than decorative. T8's consumer acquires *three* loggers,
one per logging generation, and gives all three the *identical* name, derived from the same class.
That is deliberate rather than a copy-paste defect: the class exists to compare the generations
against each other, and the arms stay comparable only while they log under a shared name. The name is
therefore carried across exactly as it stands, and one name serving several generations is never
treated as something to disambiguate.

[cols="1,3,1,2",options="header"]
|===
| ID | Logger name | Level | Message

| T8
| `org.apache.logging.log4j.PerformanceComparison`
| `DEBUG`
| `SEE IF THIS IS LOGGED 2.`

| T9
| `org.apache.logging.log4j.core.async.perftest.RunLog4j1`
| `INFO`
| `Short msg`

| T10
| `org.apache.logging.log4j.core.async.perftest.RunLog4j1`
| `INFO`
| `Short msg`
|===

T8's level and message come from its consumer's own emission, which concatenates its argument rather
than parameterising it. That concatenation is preserved: no argument anywhere in this migration was
converted to `{}` parameterisation, so the recorded message is the concatenated result. T9's and
T10's `INFO` level likewise comes from their consumer, whose three emissions are all at `INFO`, and
the message is that consumer's own latency-message constant. The sibling corpus records a different
level for one of its own fixtures because that fixture has no in-module consumer to inherit one from;
that is a sound choice for a different situation, and the two corpora are deliberately not
harmonised.

*The event script lives as Java constants inside*
`log4j-core-test/src/test/java/org/apache/logging/log4j/core/config/Log4j1MigratedConfigParityTest.java`,
never as a resource file in this directory. The sibling `log4j-perf-test` corpus keeps an equivalent
script as a resource, and this module cannot reuse it, for three independent reasons:

. `log4j-perf-test` is itself acquiring a test-scope dependency *on* `log4j-core-test`, so an edge in
  the reverse direction would be a hard Maven dependency cycle.
. `log4j-perf-test` sets `maven.deploy.skip` and `maven.install.skip` and builds no `test-jar`, so
  there is no artefact to depend on.
. The root `pom.xml` lists `log4j-core-test` *before* `log4j-perf-test`, so the edge would require
  reversing reactor order.

*This directory therefore contains exactly four files* -- the three baseline captures and this
document -- and no fifth.

== Contract for the consuming test

This document is self-sufficient by design, because the test that consumes the corpus is written
against it. The contract it must honour:

* *Boot each fixture in an isolated `LoggerContext`,* using
  `new LoggerContext(name, null, uri)`, `start()`, and `Configurator.shutdown(ctx)` to tear it down.
  The in-repository precedent is
  `log4j-core-test/src/test/java/org/apache/logging/log4j/core/appender/TlsSocketAppenderTest.java`.
  A global selector property must not be used: it would leak into every other test in the module.
* *Be order-independent and leak nothing.* Surefire runs this module with `forkCount=1C`,
  `reuseForks=false` and `runOrder=random`, so the test may not depend on execution order, and every
  context it starts must be shut down -- including on the failure path.
* *Respect the shared destination.* T9 and T10 write the same file; the test must not run them
  concurrently, and must delete the destination before each boot.
* *Stop the context before reading the file,* for the drain-and-flush reason given above.
* *Never trim, strip or collapse the text it compares.* The T9 and T10 baselines carry a significant
  trailing space, and normalising it away would make the comparison pass while hiding a real
  difference.
* *Stay within this module's API surface.* `log4j-core-test` compiles at release 8, so the test may
  not use `var`, `Files.readString`, `Files.writeString`, `String.strip`, text blocks, or
  `List.of`/`Set.of`/`Map.of`. `String.strip` and `String.trim` are doubly excluded, for the
  whitespace reason above.
* *Be clean under SpotBugs,* which is active in this module.

*Hosting these tests costs this module no build-file change at all.* `log4j-core-test` already
compiles and runs tests, already excludes `src/test/resources/**/*` from Apache RAT, holds neither
prohibited Log4j 1.x coordinate, and is not one of the five modules carrying a
`ban-logging-dependencies` enforcer execution -- so it needs no enforcer allowance either. No
dependency, no `test-jar`, no `maven-jar-plugin` execution and no `<testResources>` block was added,
and `log4j-core-test/pom.xml` is untouched by this corpus.

== Two facts recorded rather than fixed

Both of the following are pre-existing properties of the surrounding code. They are recorded because a
reader will otherwise trip over them, and *not* fixed, because fixing either would mean an
unrequested build change or an edit outside this change's permitted scope.

. *These three resources are not on the integration-test module's classpath.* `log4j-core-its` names
  all three by string literal, but they exist only in `log4j-core-test/src/test/resources`, which is
  never published: `log4j-core-test/pom.xml` contains no `test-jar` execution and no
  `maven-jar-plugin` execution, and `log4j-core-its/src/test/resources` contains only its Logback
  fixture. Those lookups therefore returned nothing before the migration and return nothing after it,
  which is precisely the behaviour preservation required. Adding a `test-jar` execution to "fix" this
  is forbidden. Capture and replay consequently execute inside `log4j-core-test`, which owns the
  resources, while the logger names, levels and messages derive from the intended consumers.
. *T8's consumer is not selected by CI.* `log4j-core-its` configures Failsafe `<groups>` with
  JUnit-4-style category class names, while `PerformanceComparison` carries a JUnit 5 `@Tag`. The
  class compiles and can be invoked explicitly, but CI does not select it, so *the absence of a
  failure report for it is not evidence that it passed.* Its migrated behaviour must be validated by
  explicit invocation.

=== The standing nearest-equivalent rules

Recorded so that a future Log4j 1.x configuration entering this repository is not translated from
first principles, and so that the one genuinely inexact mapping is not rediscovered the hard way.

* *Index shifting is the one genuine inexactness.* Log4j 1.x rolls the current file to index 1 and
  shifts every existing file up; Log4j 2 rolls to the first *available* index. Reproducing the Log4j
  1.x ordering requires `<DefaultRolloverStrategy fileIndex="min"/>`.
* `DailyRollingFileAppender` maps to `<RollingFile>` with a `+%d{...}+` `filePattern` derived from the
  Log4j 1.x `DatePattern`, plus a `<TimeBasedTriggeringPolicy>`.
* A size-triggered Log4j 1.x appender maps to a `%i` `filePattern`, a `<SizeBasedTriggeringPolicy>`
  carrying the `MaxFileSize` value, and a `+<DefaultRolloverStrategy max="..."/>+` carrying the
  `MaxBackupIndex` value.
* *Two Log4j 1.x behaviours have no exact Log4j 2 equivalent* and must be accepted as
  nearest-equivalent rather than reproduced: Log4j 1.x's compress-on-rename-only semantics, and its
  exact rename ordering under concurrent rollover.

== Record 3 -- Pattern token audit

Letter equivalence is not acceptable evidence, so each token is accounted for against *rendered
output*, and the audit is anchored in the compatibility bridge's own rewrite map rather than in a
prose comparison.

=== The bridge rewrites three tokens, then delegates to Log4j 2

`log4j-1.2-api/src/main/java/org/apache/log4j/builders/layout/PatternLayoutBuilder.java` rewrites the
Log4j 1.x conversion pattern and hands the result to Log4j 2's own `PatternLayout` builder:

[source,java]
----
.replaceAll("%([-\\.\\d]*)p(?!\\w)", "%$1v1Level")     // level names differ for custom levels
.replaceAll("%([-\\.\\d]*)x(?!\\w)", "%$1ndc")         // Log4j 1: "foo bar baz"  vs  Log4j 2: "[foo, bar, baz]"
.replaceAll("%([-\\.\\d]*)X(?!\\w)", "%$1properties")  // Log4j 1: "{{foo,bar}{hoo,boo}}"  vs  Log4j 2: "{foo=bar,hoo=boo}"
----

This is directly observable rather than merely documented. Booting the *unmodified* Log4j 1.x fixtures
through the bridge shows the rewritten effective patterns:

[source,text]
----
T8   : %d %5v1Level [%t] %c{1} %properties{transactionId} - %m%n
T9   : %d %v1Level %c{1} [%t] %properties{aKey} %m %n
T10  : %d %v1Level %c{1} [%t] %properties{aKey} %m %n
----

Two consequences follow, and they are what make this audit exact:

. *Because the bridge delegates to Log4j 2's own `PatternLayout`, every token that is neither `%p` nor
  `%X` was already being rendered by the very converter the migrated fixture now uses.* `%d`, `%t`,
  `%c{1}`, `%m` and `%n` are therefore byte-identical *by construction*, not by inspection.
. *Padding and precision survive the rewrite,* because the width is captured and re-emitted: `%5p`
  becomes `%5v1Level`, as the observed T8 pattern shows, and the same pattern parser and
  field-formatting machinery then formats both.

=== The two tokens whose converter identity changes

[cols="1,4",options="header"]
|===
| Token | Why the two converters agree here

| `%p` / `%5p`
| The bridge converter is keyed `v1Level` and appends a level that has been round-tripped *by name*;
  the native converter is keyed `p` and `level` and appends the event's level directly. Both end up
  rendering the level's own string form, so they agree for every standard level. The only case in
  which they could diverge is a custom level. *T8, T9 and T10 declare no custom level, and the
  replayed events use only the standard levels `DEBUG` and `INFO`* -- which is the precise scope of
  this claim. It is deliberately not stated more broadly: this very directory contains unrelated
  custom-level fixtures, namely `log4j-customLevel.xml`, `log4j-customLevels.xml`,
  `log4j-customLevelsOverride.xml` and `log4j-customLevelsWithFilters.xml`.

| `+%X{transactionId}+` / `+%X{aKey}+`
| Both converters take a *single-key* branch that appends the value when the key is present and
  appends nothing when it is absent. The bridge's `properties` converter and Log4j 2's `X` converter
  are byte-identical along that branch. The distinction matters because Log4j 2's whole-map and
  multiple-key branches would instead render `{}` on empty data -- but neither fixture uses a bare
  `%X` or a multi-key form, so neither takes those branches. With the key unset, as in both captures,
  both worlds render *the empty string*.
|===

=== `%c{1}` renders the full simple logger name

An all-digits option selects the abbreviator strategy documented as retaining a given number of parts
counted from the end, with one part retained. The captures accordingly show `PerformanceComparison`
and `RunLog4j1` in full, never a dot-abbreviated form.

=== The whitespace that the empty single-key rendering produces

This is the audit's most easily mistaken result, so it is stated explicitly. Because an absent
single-key context value renders as the empty string:

* *T8* renders `%c{1}`, a space, the empty string, a space, then `-`, producing *a double space
  immediately before the `-` separator*.
* *T9 and T10* render `]`, a space, the empty string, a space, then the message, producing *a double
  space between `]` and the message*; and because their pattern ends `%m %n` with a real space, every
  rendered line also carries a *significant trailing space* before the line separator.

All three are correct, byte-identical behaviour. *Trimming, collapsing or right-stripping whitespace,
in a fixture or in a baseline, is a defect,* and it is why the consuming test may not use `String.trim`
or `String.strip` on the text it compares.

=== Translations were made from the Log4j 1.x source, never from an in-repository Log4j 2 peer

This prohibition earned its keep. `log4j-perf-test/src/main/resources/log4j2-perfloc.xml`, an
independently authored Log4j 2 benchmark peer, uses `+%C{1.}+` where its Log4j 1.x counterpart uses
`+%C{1}+`. Those select *different* abbreviation strategies and render differently, so copying the peer
would have silently broken parity. Every translation here was therefore derived from the Log4j 1.x
source text. In this directory `perf5AsyncApndNoLoc.xml`, `perf6AsyncApndLoc.xml`, `log4j2-perf.xml`
and `perf-CountingNoOpAppender.xml` are all independently authored peers; none was copied from, and
none was edited.

=== Tokens confirmed absent

No audit row is owed for any of the following, because none appears in T8, T9 or T10 and none was
introduced: `%x` and any nested-diagnostic-context use, bare `%X`, `%properties`, `%v1Level`, `%r`,
`%C`, `%M`, `%L`, any explicit throwable specifier, and the TTCC, Simple, HTML and XML layouts.
Because no pattern names an explicit throwable specifier, a plain throwable converter is appended
implicitly -- identically in both worlds, since both delegate to the same `PatternLayout` -- so
throwable rendering would be compared byte for byte if a throwable were ever added to the script.

== Record 4 -- Rule 6 arbitration outcomes

Where the translation could reasonably have gone two ways, baseline observed output is the
tie-breaker. Each open question is recorded below as a decision with its evidence. In every case the
normalized diff came back empty, so none of these decisions was made to *rescue* a failing
comparison; they were made to choose between alternatives the comparison could not distinguish, and
the tie-break criterion was then "reproduce genuine Log4j 1.x rather than an approximation of it".

=== Decision 1 -- T8 omits `bufferedIo` entirely

*Decision: omit the attribute.* The Log4j 1.x source declares no `BufferedIO` parameter, so there is no
value to carry across; the open question was whether to state Log4j 1.x's default explicitly.

. *Genuine Log4j 1.x was observed with buffered I/O off and an 8192-byte writer buffer.* Log4j 2's
  default buffer size is also 8192 -- it is defined as an 8 KiB encoder byte-buffer -- so leaving
  `bufferedIo` unset yields a live 8192-byte buffer, which is the same disposition.
. *Writing `bufferedIo="false"` would be worse, and provably so.* A control run adding that attribute
  to a copy of the fixture raised
  `WARN The bufferSize is set to 8192 but bufferedIo is false: false`
  and degraded the appender to per-event writes that Log4j 1.x never performed.
+
[IMPORTANT]
====
The file appender carries *two distinct* guard warnings and they must not be conflated. The one above
is the buffer-size-versus-buffering warning. The separate warning
`+Locking and buffering are mutually exclusive. No buffering will occur for {}+`
requires file locking to be switched on, which none of these fixtures does, and is *not* relevant
here. Neither warning fires for any of the three fixtures as translated.
====
. *The baseline confirms the choice.* With the attribute omitted, T8's normalized diff is *empty*.
  Buffering governs only *when* bytes reach the disk, never *what* is written, so the comparison could
  not have distinguished the two spellings -- and the omitted form is the one that matches genuine
  Log4j 1.x while emitting strictly fewer diagnostics.

=== Decision 2 -- T9 and T10 state `immediateFlush="false"` although their source never does

*This one is determined rather than arbitrated,* and it is the single most likely place for a faithful
looking translation to change behaviour silently.

Log4j 1.x *couples* buffering to flushing: its file-appender builder forces the flush flag off whenever
buffered I/O is on, in effect `if (bufferedIo) { immediateFlush = false; }`, over declared defaults of
append on, immediate flush on, buffered I/O off and an 8192-byte buffer. Log4j 2 does not couple them:
its output-stream appender builder defaults buffered I/O *on*, the buffer to the 8 KiB encoder size,
and immediate flush *on*, all independently.

The coupling is observable, not inferred. Genuine Log4j 1.x reports `immediateFlush=false` for T9 and
T10 even though neither source declares an `ImmediateFlush` parameter -- the value exists only because
`BufferedIO=true` forced it. Log4j 2 will not make that inference, so the flush setting must be stated
explicitly. *Omitting it would have turned a buffered configuration into one that flushes on every
event* -- a change in the exact disposition a benchmark fixture exists to hold still.

=== Decision 3 -- T10 states `blocking="true"` although it is also the Log4j 2 default

*Decision: state it explicitly.* Two reasons, and one observation that has to be handled carefully.

. *Genuine Log4j 1.x blocks by default.* Disassembling the published Log4j 1.2.17 artefact shows its
  asynchronous appender's no-argument constructor storing *true* into its blocking field, alongside
  128 for the buffer size and false for location capture. Genuine Log4j 1.x therefore applies
  back-pressure when the queue fills, and `blocking="true"` reproduces that.
. *The bridge does not.* Booting the unmodified Log4j 1.x fixture through the bridge shows the
  asynchronous appender built with blocking *off*, because the bridge only overwrites its flag when
  the source declares a `Blocking` parameter and this source declares none. That value is an artefact
  of the bridge, not Log4j 1.x behaviour, and reproducing it would have been the wrong target.
. *The baseline cannot arbitrate this attribute, which is why it is stated rather than left to a
  default.* Blocking governs only what happens when the queue is *full* -- wait for space, or discard.
  The queue holds 262144 events and the script emits one, so the full path is never taken; a control
  run with `blocking="false"` produced a capture byte-identical to the committed baseline. Since the
  comparison is blind to it, the conservative choice for a measurement instrument is to preserve
  back-pressure and to make that visible to a reviewer. Discarding events would also breach the
  requirement that nothing be added, removed or re-levelled.

=== Decision 4 -- no `additivity` attribute is added, although the observed root flag differs

*Decision: add nothing.* This is the one row in the corpus whose raw observed values differ, and it is
recorded rather than smoothed over.

. *What was observed.* Genuine Log4j 1.x reports the root logger's additivity as `true`. The migrated
  fixtures declare no `additivity` attribute -- the boot trace shows it unset -- and the built root
  object reports `false`, because Log4j 2's root-logger plugin builder holds this attribute in a
  primitive field, so an unset attribute yields `false`. This is how *every* `<Root>` element in this
  repository behaves; it is not a property of these translations.
. *Why the difference is inert here.* Additivity controls whether a logger's events are *also* passed
  to its parent's appenders. The root has no parent, so its own flag can propagate nothing. Moreover
  all three configurations declare *no logger other than the root*, so there is no additive
  propagation path in the configuration at all -- there is no child logger whose events could be
  duplicated or dropped.
. *A control run confirms it is inert.* Adding `additivity="true"` to a copy of T8 makes the built root
  report `true`, matching genuine Log4j 1.x exactly, *and leaves the normalized capture byte-identical
  to the committed baseline.* The attribute therefore buys no behavioural change, so it is omitted,
  keeping each translated fixture free of anything its Log4j 1.x source did not state.

=== A note on the bridge as a reference point

One further observation is recorded because it vindicates two of the decisions above and would
otherwise look like an inconsistency. For T8, the bridge reports `immediateFlush=true` -- it does not
honour the source's explicitly declared flush parameter, and capitalising that parameter's name does
not change the outcome -- whereas genuine Log4j 1.x reports `false`. The bridge is therefore an
*approximation* of Log4j 1.x in two of the places this corpus touches: T8's flush flag and T10's
blocking flag. In both, the translated fixture matches *genuine* Log4j 1.x rather than the bridge, and
in both the rendered output is identical regardless. That is the correct target: the migration is away
from Log4j 1.x, not away from the bridge's rendition of it.
