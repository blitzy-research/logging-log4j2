= Log4j 1.x to Log4j 2 configuration parity corpus: effective configuration (T8-T10)

This directory is the behaviour-preservation oracle for the three Log4j 1.x configuration fixtures
that were translated in place into the Log4j 2 schema inside `log4j-core-test/src/test/resources`.

It exists to turn "behaviour preserved" from a claim into something a reviewer can check. Each
translated fixture contributes two artefacts:

* a *normalized baseline capture* -- `<fixture>.baseline.txt` -- recording exactly what the Log4j 1.x
  configuration rendered before the migration, and
* an *effective-configuration table* in this document, whose Log4j 2 column is populated from what
  was observed while booting the translated file with `-Dlog4j2.debug`, never from reading the
  translated XML.

*Acceptance for every fixture is an empty normalized diff* between its baseline capture and the
output the migrated configuration renders for the same event. A non-empty diff is a defect in the
migration. It is never resolved by widening the normalizer, and never by editing a baseline.

== How both columns were observed

The method is prescribed, not merely the goal:

[quote]
____
each translated configuration file is to be booted with `-Dlog4j2.debug`, and its effective logger
levels, additivity, and appender wiring compared against a documented table derived from the 1.x
original.
____

Accordingly, *the Log4j 2 column is populated from observed boot output and from interrogating the
objects the running configuration actually built.* Reading the translated XML and transcribing its
attributes is exactly what this directive forbids, and it is not what was done. `log4j2.debug` is a
real, supported property, declared in
`log4j-api/src/main/java/org/apache/logging/log4j/status/StatusLogger.java`; when it is set, status
level filtering is bypassed so that every status event reaches listeners. The constant holding its
name is `private`, so it is set as a JVM system property (`-Dlog4j2.debug`) and never referenced
programmatically.

Three independent observation arms were run, each booting a fixture, replaying the event script,
stopping the logger context and reading back the rendered file:

[cols="1,3,3",options="header"]
|===
| Arm | What it ran | What it establishes

| *Genuine Log4j 1.x*
| The unmodified 1.x fixture under the real `log4j:log4j:1.2.17` artefact, with no bridge and no
  Log4j 2 on the classpath, selected with `-Dlog4j.configuration`
| The authoritative *Observed, Log4j 1.x* column. This is what "the 1.x original" means: the library
  the fixtures were written against

| *Bridge*
| The same unmodified 1.x fixture through the `log4j-1.2-api` compatibility bridge, selected with
  `-Dlog4j.configuration` plus the experimental compatibility flag. *This arm is an arrangement the
  transient harness constructed on purpose; it is NOT a path any of these three fixtures took in the
  repository.* At the base commit none of T8, T9 or T10 was on the runtime classpath of any module that
  declared the bridge -- as the consumer discussion under each fixture below records -- so nothing here
  ran through the bridge unless the harness deliberately routed it there
| *Corroboration only, never authority.* Its sole purpose is to expose two places where the bridge is an
  *approximation* of Log4j 1.x rather than a reproduction of it. Where the two 1.x arms disagree, the
  genuine artefact decides and the bridge is recorded as the deviation

| *Log4j 2*
| The translated fixture in an isolated `LoggerContext`, with only `log4j-api` and `log4j-core` on
  the classpath
| The *Observed, Log4j 2* column, and the rendered output that is diffed against the baseline
|===

*A row is accepted only when the Log4j 1.x-observed and Log4j 2-observed values agree.* *Every row in
all three tables agrees, with exactly one named exception*: root additivity, where Log4j 1.x reports
`true` and the translated fixtures report `false`. No other row is accepted on the strength of a
difference being argued inert, and no further exception may be added to this one.

That exception is discharged in Record 4, by proof that the flag cannot be consulted at all for a logger
with no parent -- carried in Core's own source and in measurement, not in reasoning alone. An intermediate
state of this corpus closed the row *literally* instead, by adding `additivity="true"` to all three
translated roots; that attribute has been removed, because it has no counterpart in the Log4j 1.x sources
being translated and the target design for these fixtures carries the level on the root element and
nothing else. Additivity is *asserted from observation* in all three tables -- never assumed from a
documented default, which for the root logger is not the value one would expect.

The harness that drove the two Log4j 1.x arms is transient and *is not committed*. It necessarily used
the `org.apache.log4j` facade, and the rule that would have forbidden committing it is a *scoped* one:
the migrated consumers carry no import of that package and no declaration typed against it. That is the
claim the source oracle checks -- over `git ls-files '*.java'` with the `log4j-1.2-api` module excluded,
because the bridge implements the namespace and must therefore name it -- and every migrated call site
satisfies it. Only the normalized captures are committed; the harness is not among them.

Stated repository-wide the claim would be false, so it is stated with its exceptions instead. Two
references survive *by decision*, both of them in `log4j-osgi-test`, and both verifying that this
project's *own shipped* bridge bundle resolves and logs rather than routing anything around this
migration:

* `CoreOsgiTest.java` L81 is a genuine fully-qualified typed call site, compiled against the single
  test-scope bridge dependency that the enforcer allowance carves out.
* `AbstractLoadBundleTest.java` L147 loads `org.apache.log4j.Level` reflectively, from a string literal,
  through the bundle class loader.

Both files were reviewed and deliberately left unchanged. The migration's own summary of the oracle names
only the reflective literal as its known exception; the typed call site is the second, and it is retained
under the same decision -- deleting either would destroy the only coverage of a published artefact.

Four further files name the namespace -- in six places -- without resolving it as a logging facade, and
not one of them is a migrated consumer's call site: Log4j 2 Core's own `OptionConverter` helper carries
the name in a comment and in a warning message; `log4j-api`'s internal `package-info.java` lists the
bridge's package as an OSGi and JPMS export target; the message-resolver test that this migration
converted to the native facade keeps the superseded call's name in a comment and inside the message text
it asserts on; and the website's migration example imports the facade on purpose, being a documentation
snippet that Spotless format-checks and no compiler ever compiles.

Inside this directory this document is the only file that names the Log4j 1.x namespace at all -- the
three baselines are rendered output and name nothing. It does so in four ways, every one of them inert:
*twelve* class names inside the tables below, of which five quote a superseded fixture's `class=`
attribute verbatim and seven report the classes Log4j 1.x was *observed* to instantiate; *one* class name
in prose, the level class the OSGi test loads reflectively; *three* citations of evidence paths, in slash
form; and the bare package name *once*, where the harness is described above. Seventeen mentions, not one
of which is an import, a declaration, or anything a class loader is asked to resolve.

== Normalization

Exactly four tokens are normalized, and nothing else:

[cols="2,1,4",options="header"]
|===
| Rendered element | Normalized to | Why

| `%d` timestamp
| `<TS>`
| Wall-clock, non-deterministic.

| `%t` thread name
| `<THREAD>`
| The *producing* thread: the one that emitted the event, recorded when the event was *constructed*.
  It is *never* the asynchronous dispatcher that later writes the event out -- which matters here,
  because T10 wraps its appender in the asynchronous one, and both generations capture the producer's
  name before the event is enqueued. Only the *value* is non-deterministic, being harness-assigned and
  run-dependent; the fact that it identifies the producer is preserved, and the sibling corpus records
  the observation that establishes it.

| `%L` source line number
| `<LINE>`
| A source-layout artefact of the migration itself, which shifts whenever lines above an emission are
  edited. *Inert in this corpus:* none of T8, T9 or T10 uses `%C`, `%M` or `%L`, so the rule never
  fires here. It is retained so that this module's normalizer stays byte-identical to the sibling
  module's. *Class and method names are never normalized* -- only the line number would have been.

| Absolute filesystem paths
| `<PATH>`
| Workspace-dependent.
|===

Everything outside those four tokens is compared byte for byte: level text *and its padding width*,
logger-name abbreviation, every literal separator, context-map placeholder rendering, and throwable
rendering.

*Normalization is line-aware, not a sequence of global replacements,* and that distinction is
load-bearing rather than stylistic. A timestamp is recognised only where a rendered event actually
begins one, at the start of a line; the thread and source-line substitutions are applied at most once
per line, and only on a line that carries a timestamp. The reason is that two of the four regions are
not unambiguous in isolation -- a thread name renders inside square brackets, and a message may itself
contain a bracketed group, so replacing that pattern globally would rewrite message text, and a
timestamp-shaped substring inside a message would be rewritten as though it were an event's own.
Absolute paths carry no such ambiguity and are replaced throughout, which is what lets a stack-trace
continuation line be normalized without being mistaken for an event. Line structure is preserved
exactly, so whether a capture ends with a line separator survives untouched, and every substitution is
idempotent, which is what makes it safe to normalize a committed baseline as well as a capture. This is
the same algorithm the sibling module's corpus applies, expressed against the API surface this module
compiles to, with the same four patterns and the same four replacement tokens character for character.

Two whitespace consequences are load-bearing and are called out here because they look like
formatting noise and are not:

* T8's baseline contains a *double space immediately before the `-` separator*.
* T9's and T10's baselines contain a *double space* after `]` and a *significant trailing space*
  before the line separator.

Both fall out of correct, byte-identical behaviour, and both are explained in Record 3. Trimming,
right-stripping or collapsing whitespace in a baseline is a defect. `grep -nP '[ \t]$'` is *expected*
to match the T9 and T10 baselines.

Because that expectation collides with the repository's standard whitespace check, the root
`.gitattributes` exempts *only* `+*.baseline.txt+` under this directory and its sibling from the
end-of-line blank check:

----
/log4j-core-test/src/test/resources/log4j1-parity/*.baseline.txt whitespace=-blank-at-eol
----

Nothing else is exempted -- not this document, not any source file, and no other whitespace check on
these files -- and *no capture byte is altered*: `git diff --check` passes with the trailing space still
present in both the file and its staged blob. The sibling corpus records the full reasoning, including
why a whitespace-safe re-encoding of the captures was rejected in favour of keeping the payload
literal.

== Capture ordering and capture hygiene

The baselines were captured *before the migration landed*, which is the only order in which they can
arbitrate anything:

[cols="1,3",options="header"]
|===
| Condition | Value

| Base commit
| `df1d9a5198c55339cc4eebe78030f4fbdf4d5070`, branch `2.x`

| JDK
| 17, per `.java-version`

| Maven
| 3.9.16, per `.mvn/wrapper/maven-wrapper.properties`

| Classpath state
| The Log4j 1.x classpath was still present; no dependency had been removed and no fixture had been
  translated

| Committed artefacts
| The normalized captures only. The capture harness is not committed
|===

Three disciplines were mandatory during capture, and remain mandatory for anything that reproduces
it:

. *T9 and T10 share a destination.* Both write the bare relative path `perftest.log`. They are never
  booted concurrently, and the destination is deleted immediately before each boot. Only T8 writes
  `target/testlog4j.log`, and it is deleted before its own boot for the same reason.
. *The context is stopped before the file is read.* T10 is asynchronous, and T9 and T10 both carry
  `immediateFlush="false"`, so when the last emission returns events may still be queued and rendered
  bytes may still be sitting in the encoder buffer. Stopping the context drains the queue into the
  file appender and then flushes it, which makes the read a result rather than a race.
. *Nothing is tuned to make output appear.* These fixtures serve a benchmark harness -- a measurement
  instrument. Waiting on a timer instead of stopping the context, relaxing `immediateFlush`,
  shrinking `bufferSize`, or replacing the asynchronous appender with a synchronous one would each
  make output appear sooner while destroying the very disposition being preserved. None was done, and
  none may be done.

== The event script, and where it lives

Each fixture is exercised by *exactly the emission its real consumer makes*, and by nothing else. The
logger names, levels and messages are carried across character for character; logger names in
particular are never "improved". No probe, control or otherwise invented event appears anywhere in this
script, and none may be added: an event no consumer emits was never rendered by the superseded
generation, so no capture of it exists and it can prove nothing about the translation.

One case makes that rule load-bearing rather than decorative. T8's consumer acquires *three* loggers,
one per logging generation, and gives all three the *identical* name, derived from the same class.
That is deliberate rather than a copy-paste defect: the class exists to compare the generations
against each other, and the arms stay comparable only while they log under a shared name. The name is
therefore carried across exactly as it stands, and one name serving several generations is never
treated as something to disambiguate.

[cols="1,3,1,2,2",options="header"]
|===
| ID | Logger name | Level | Message | Origin

| T8
| `org.apache.logging.log4j.PerformanceComparison`
| `DEBUG`
| `SEE IF THIS IS LOGGED 2.`
| consumer emission

| T9
| `org.apache.logging.log4j.core.async.perftest.RunLog4j1`
| `INFO`
| `Short msg`
| consumer emission

| T10
| `org.apache.logging.log4j.core.async.perftest.RunLog4j1`
| `INFO`
| `Short msg`
| consumer emission
|===

T8's level and message come from its consumer's own emission, which concatenates its argument rather
than parameterising it. That concatenation is preserved: no argument anywhere in this migration was
converted to `{}` parameterisation, so the recorded message is the concatenated result. T9's and
T10's `INFO` level likewise comes from their consumer, whose three emissions are all at `INFO`, and
the message is that consumer's own latency-message constant.

The sibling `log4j-perf-test` corpus carries one entry naming that very same consumer class, for its own
copy of the asynchronous fixture, and it records that entry at `INFO` too. *The two corpora agree, as two
records of one real emission must.* Neither level was chosen to match a root level: every one of that
consumer's three emissions is at `INFO`, so `INFO` is the only level either corpus may record for it, and
both fixtures declare a `debug` root that admits it. The two committed captures are byte-identical in
consequence -- 43 bytes each, `+<TS> INFO RunLog4j1 [<THREAD>]  Short msg +` including the significant
trailing space -- and that cross-corpus identity is itself a check: a divergence between them would mean
one of the two had substituted a level no capture evidences for one that a capture does, which is
precisely the drift these gates exist to prevent.

=== The `+%5p+` field width, and how it is verified without an invented event

T8's layout renders the level through `+%5p+` -- a five-character minimum field. Its consumer's own
emission is at `DEBUG`, which is *exactly five characters*, so it needs no padding and its bytes are
identical to those the same event would produce through a bare `+%p+`. The rendered capture therefore
cannot, on its own, distinguish the width from its absence: deleting the width from the translated
pattern would leave `log4j12-perf.baseline.txt` unchanged.

*The gap is closed by observation, not by invention.* The layout-pattern row of T8's
effective-configuration table below is populated from the configuration the migrated fixture actually
boots, read out of its `-Dlog4j2.debug` status output, and it is compared against the pattern the
superseded fixture configured *character for character* -- `+%5p+` included. A translated pattern whose
width had been deleted would fail that row immediately, while rendering identical bytes. The width is
thus verified by the evidence route this document is for, rather than by the rendered-output route,
which for this one token has nothing to say.

The alternative -- replaying an extra event at a shorter level so that the padding becomes visible in
the bytes -- was considered and *rejected*, for a reason that outweighs the convenience:

* *No such event was ever captured.* The superseded generation rendered exactly what its consumer
  emitted. A shorter-levelled line added to this corpus would be a line this project computed, not a
  line it recorded, and a baseline that contains computed bytes is no longer an oracle: it can only
  ever confirm the reasoning that produced it.
* *It would misrepresent the consumer.* The comparison class emits one event on this logger, at
  `DEBUG`. Recording a second, at another level, states something about the consumer that is not true.
* *The corpus rule is explicit.* Every record in this script is a consumer emission; admitting one
  exception would make the rule unenforceable, and the same exception was already removed from the
  sibling corpus for the same reason.

T9 and T10 are owed no equivalent discussion: their pattern renders the level through a bare `+%p+`, so
there is no width to verify at all.

=== Where the script lives

*The event script is to live as Java constants inside*
`log4j-core-test/src/test/java/org/apache/logging/log4j/core/config/Log4j1MigratedConfigParityTest.java`,
never as a resource file in this directory.

[NOTE]
.State of the consuming test
====
*That test class now exists* and consumes this corpus: `Log4j1MigratedConfigParityTest.java` is in the
tree beside the other configuration tests, and it runs three independent cases, one per fixture. The
table above and the class's own constants must agree; the table remains deliberately complete so that
either can be checked against the other. The corpus nevertheless precedes the test in time, and that
ordering is not incidental: the baselines had to be captured while the Log4j 1.x classpath still
existed, which is no longer the case, whereas the test was written afterwards against the committed
evidence. That is why the captures are oracles and the test is their consumer, never the reverse.
====

The sibling `log4j-perf-test` corpus keeps an equivalent script as a resource, and this module cannot
reuse it, for three independent reasons:

. `log4j-perf-test` is itself acquiring a test-scope dependency *on* `log4j-core-test`, so an edge in
  the reverse direction would be a hard Maven dependency cycle.
. `log4j-perf-test` sets `maven.deploy.skip` and `maven.install.skip` and builds no `test-jar`, so
  there is no artefact to depend on.
. The root `pom.xml` lists `log4j-core-test` *before* `log4j-perf-test`, so the edge would require
  reversing reactor order.

*This directory therefore contains exactly four files* -- the three baseline captures and this
document -- and no fifth.

== Contract for the consuming test

This document is self-sufficient by design, because the test that consumes the corpus was written
against it. Every item below is a standing requirement on that test, and each is honoured by the class
now in the tree; the list is kept as a contract rather than rewritten as a description, so that a future
change to the test can be checked against it:

* *Boot each fixture in an isolated `LoggerContext`,* using
  `new LoggerContext(name, null, uri)`, `start()`, and `Configurator.shutdown(ctx)` to tear it down.
  The in-repository precedent is
  `log4j-core-test/src/test/java/org/apache/logging/log4j/core/appender/TlsSocketAppenderTest.java`.
  A global selector property must not be used: it would leak into every other test in the module.
* *Be order-independent and leak nothing.* Surefire runs this module with `forkCount=1C`,
  `reuseForks=false` and `runOrder=random`, so the test may not depend on execution order, and every
  context it starts must be shut down -- including on the failure path.
* *Respect the shared destination.* T9 and T10 write the same file; the test must not run them
  concurrently, and must delete the destination before each boot.
* *Stop the context before reading the file,* for the drain-and-flush reason given above.
* *Never trim, strip or collapse the text it compares.* The T9 and T10 baselines carry a significant
  trailing space, and normalising it away would make the comparison pass while hiding a real
  difference.
* *Compare the whole of every capture,* never only a first line and never only a prefix. The whole file
  is read as bytes and decoded in one step, so the presence or absence of the terminating line separator
  is part of the comparison too.
* *Keep rendered output as the oracle.* The committed capture is what arbitrates: the test asserts an
  empty normalized diff against it, and no structural check may stand in for that comparison or soften
  it. Nothing is read from the configuration *files*, because reading the translation and then asserting
  what was read is circular.
* *Judge parity on rendered output alone.* The dimensions rendered bytes cannot see -- a started XML
  configuration rather than a fallback; the root logger's level and additivity; the file appender's
  destination, its `immediateFlush`, its `isAppend()` and its resolved byte buffer; and T10's asynchronous
  wrapper with its queue capacity, its blocking behaviour and its absence of caller-location capture -- are
  evidenced by the observed effective-configuration tables below, each populated from a `-Dlog4j2.debug`
  boot and cross-checked against the superseded fixture. They are deliberately *not* re-asserted inside the
  test through `Configuration`, `Appender`, `FileManager`, `PatternLayout`, `XmlConfiguration` or
  plugin-builder state: the committed capture is this corpus's oracle, and a structural check standing
  beside it would be a second, weaker oracle able to pass while the capture diverged. The one dimension a
  `DEBUG`-only capture genuinely cannot show, T8's `+%5p+` field width, is settled the same way -- by the
  observed conversion pattern in T8's table below, never by reading the translated file back.
* *Pin each case to its own resource, and leave no lookup for a fallback to win.* The case resolves the
  classpath resource it named, asserts that it is there, and hands the context that resource's own URI, so
  the configuration in force can be neither a fallback nor a sibling fixture. All three fixtures here are
  XML and T9 and T10 bind the same appender name to the same destination, so that identity matters -- and
  it is established by construction rather than by inspecting the configuration the boot produced.
* *Require the boot to be quiet at `WARN` or above, and establish it from the recorded boot.* An unresolved
  appender reference, an unrecognised attribute and a silent fallback are all reported through the status
  channel and *none* of them stops a context from starting or a case from producing a file. Every boot
  recorded in this document was therefore taken under `-Dlog4j2.debug`, which routes the whole channel to
  the console, and read for anything at `WARN` or above before its row was accepted; all three fixtures
  boot, replay and stop with nothing recorded at either level. The reading is taken at `WARN` and not at
  `ERROR` because `StatusLogger` dispatches to its fallback listener only while no listener is registered
  and that fallback's own default threshold is `ERROR`, so an error-only reading would miss a warning about
  a mis-resolved reference or an unparsed option in both channels at once. The test itself registers no
  status listener: a listener is process-global state, and this module runs with `forkCount=1C`,
  `reuseForks=false` and `runOrder=random`, so each case asserts only what it can own.
* *Stay within this module's API surface.* `log4j-core-test` compiles at release 8, so the test may
  not use `var`, `Files.readString`, `Files.writeString`, `String.strip`, text blocks, or
  `List.of`/`Set.of`/`Map.of`. `String.strip` and `String.trim` are doubly excluded, for the
  whitespace reason above.
* *Be clean under SpotBugs* -- established by a run that actually analyses it. SpotBugs is active in this
  module, but the goal as configured analyses main classes only, so the normal build cannot establish
  anything about a *test* class: this module's default report holds 73 `FileStats` entries and mentions
  this test *zero* times. Cleanliness was therefore established by including test classes explicitly,
  `+mvn -pl log4j-core-test verify -DskipTests -Dspotbugs.includeTests=true+`, whose report holds 652
  `FileStats` entries and records
  `+<FileStats path='org/apache/logging/log4j/core/config/Log4j1MigratedConfigParityTest.java' ...
  bugCount='0'>+`. That run reports 14 bug instances in total, every one of them in a pre-existing class
  of this module -- two in a GC-pressure generator, one in a progress-console test, two in JDBC appender
  tests, two in Kafka appender tests, five ignored return values, and two more in map and string-layout
  tests -- and none in this test. Those pre-existing findings are why the run exits non-zero, and why the
  claim made here is scoped to this file rather than to the module.

*Hosting these tests costs this module no build-file change at all.* `log4j-core-test` already
compiles and runs tests, already excludes `src/test/resources/**/*` from Apache RAT, holds neither
prohibited Log4j 1.x coordinate, and is not one of the five modules carrying a
`ban-logging-dependencies` enforcer execution -- so it needs no enforcer allowance either. No
dependency, no `test-jar`, no `maven-jar-plugin` execution and no `<testResources>` block was added,
and `log4j-core-test/pom.xml` is untouched by this corpus.

== Two facts about the consumers, and what each one required

Both of the following are properties of the surrounding code rather than of these three fixtures. Both are
recorded because a reader will otherwise trip over them, and both are left as observations: neither is
"`fixed`" in a consumer or in a build file, because neither remedy is within the change permitted to those
files.

. *These three resources are not on the integration-test module's classpath, and the consumers had to be
  made to survive that.* `log4j-core-its` names all three by string literal, but they exist only in
  `log4j-core-test/src/test/resources`, which is never published: `log4j-core-test/pom.xml` contains no
  `test-jar` execution and no `maven-jar-plugin` execution, and `log4j-core-its/src/test/resources`
  contains only its Logback fixture. Adding a `test-jar` execution to "`fix`" this is forbidden, and
  putting this module's test-resource directory on the consumers' class path was rejected on measurement:
  that directory holds 310 entries at its top level and 535 files in all, among them a `logback-test.xml`
  that would collide with the integration-test module's own and silently re-configure the out-of-scope
  Logback arm, and a `META-INF/services/org.apache.logging.log4j.spi.TraceContextProvider` registration.
  Class-path entries cannot be made file-selective.
+
What *is* preserved by the lookups returning nothing is only the lookup result. The effective level is
not: a context handed no resolvable configuration falls back to Log4j 2's default, whose root logger is
at `ERROR`, whereas the superseded generation under the identical condition kept a root level of `DEBUG`
and owned no appender. Measured against the genuine `log4j:log4j:1.2.17` artefact:
`+root.getLevel()=DEBUG+`, `+isDebugEnabled()=true+`, `+isInfoEnabled()=true+`, root appender count
*zero*.
+
The two consumers of these fixtures are treated differently, and the difference is *prescribed* rather
than chosen. `PerformanceComparison`, which consumes T8, is one of the seven classes authorised to hold an
isolated logger context, because it drives three logging generations inside a single JVM and one global
configuration property could only ever select one of them. Its authorised change is exactly five hunks --
three imports, the logger declaration, the removal of the superseded selector constant with its two property
calls, the context construction and its teardown -- so when the fixture does not resolve it passes the
unresolved location on as a null URI rather than building a hierarchy in code, and it adds no assertion. The
consequence is stated rather than engineered away: that context falls back to Log4j 2's default, so in this
environment the arm's timed `debug` call is a level check instead of an emission -- as the native arm's
already is, since `log4j2-perf.xml` is owned by another module on exactly the same terms and produces the
identical `+ERROR Reconfiguration failed+` status line in the same run. Both Log4j arms therefore sit in the
same unconfigured state, which is what keeps their comparison meaningful. `RunLog4j1`, which consumes T9 and
T10, is deliberately *not* authorised to hold a context at all: its change is the two-line import
substitution and nothing else, on the recorded ground that the driver launches one child JVM per row, so
those arms never share a configuration namespace once the superseded selector stops being forwarded. Its
`info` calls consequently resolve against whatever configuration the child's own class path yields, which
for a row name that resolves to nothing is Log4j 2's default. That asymmetry is the shape the plan fixes for
these two files, and it is recorded here so that a reader does not mistake it for an oversight.

the resources, while the logger names, levels and messages derive from the intended consumers -- so the

=== Proof of absence

| 0

| Log4j 1.x `RollingFileAppender`
| 0

| `MaxFileSize`
| 0

| 0

| `DatePattern`
| 0
|===

*Zero rolling-policy mappings are applied,* and no rolling appender, triggering policy or rollover
strategy was introduced into any translated fixture.

=== The standing nearest-equivalent rules

Recorded so that a future Log4j 1.x configuration entering this repository is not translated from
first principles, and so that the one genuinely inexact mapping is not rediscovered the hard way.

* *Index shifting is the one genuine inexactness.* Log4j 1.x rolls the current file to index 1 and
  shifts every existing file up; Log4j 2 rolls to the first *available* index. Reproducing the Log4j
  1.x ordering requires `<DefaultRolloverStrategy fileIndex="min"/>`.
* `DailyRollingFileAppender` maps to `<RollingFile>` with a `+%d{...}+` `filePattern` derived from the
  Log4j 1.x `DatePattern`, plus a `<TimeBasedTriggeringPolicy>`.
* A size-triggered Log4j 1.x appender maps to a `%i` `filePattern`, a `<SizeBasedTriggeringPolicy>`
  carrying the `MaxFileSize` value, and a `+<DefaultRolloverStrategy max="..."/>+` carrying the
  `MaxBackupIndex` value.
* *Two Log4j 1.x behaviours have no exact Log4j 2 equivalent* and must be accepted as
  nearest-equivalent rather than reproduced: Log4j 1.x's compress-on-rename-only semantics, and its
  exact rename ordering under concurrent rollover.

== Record 3 -- Pattern token audit

Letter equivalence is not acceptable evidence, so each token is accounted for against *rendered
output*, and the audit is anchored in the compatibility bridge's own rewrite map rather than in a
prose comparison.

=== The bridge rewrites three tokens, then delegates to Log4j 2

`log4j-1.2-api/src/main/java/org/apache/log4j/builders/layout/PatternLayoutBuilder.java` rewrites the
Log4j 1.x conversion pattern and hands the result to Log4j 2's own `PatternLayout` builder:

[source,java]
----
.replaceAll("%([-\\.\\d]*)p(?!\\w)", "%$1v1Level")     // level names differ for custom levels
.replaceAll("%([-\\.\\d]*)x(?!\\w)", "%$1ndc")         // Log4j 1: "foo bar baz"  vs  Log4j 2: "[foo, bar, baz]"
.replaceAll("%([-\\.\\d]*)X(?!\\w)", "%$1properties")  // Log4j 1: "{{foo,bar}{hoo,boo}}"  vs  Log4j 2: "{foo=bar,hoo=boo}"
----

This is directly observable rather than merely documented. Booting the *unmodified* Log4j 1.x fixtures
through the bridge shows the rewritten effective patterns:

[source,text]
----
T8   : %d %5v1Level [%t] %c{1} %properties{transactionId} - %m%n
T9   : %d %v1Level %c{1} [%t] %properties{aKey} %m %n
T10  : %d %v1Level %c{1} [%t] %properties{aKey} %m %n
----

Two consequences follow, and they are what make this audit exact:

. *Because the bridge delegates to Log4j 2's own `PatternLayout`, every token that is neither `%p` nor
  `%X` was already being rendered by the very converter the migrated fixture now uses.* `%d`, `%t`,
  `%c{1}`, `%m` and `%n` are therefore byte-identical *by construction*, not by inspection.
. *Padding and precision survive the rewrite* as a matter of mechanism, because the width is captured
  and re-emitted: `%5p` becomes `%5v1Level`, as the observed T8 pattern shows, and the same pattern
  parser and field-formatting machinery then formats both. *This mechanism is corroboration, not the
  evidence.* Rewrite mechanics cannot establish rendered padding, and the committed captures cannot
  either -- see the measurement below, which supplies the observed rendering the rule actually demands.

=== The two tokens whose converter identity changes

[cols="1,4",options="header"]
|===
| Token | Why the two converters agree here

| `%p` / `%5p`
| The bridge converter is keyed `v1Level` and appends a level that has been round-tripped *by name*;
  the native converter is keyed `p` and `level` and appends the event's level directly. Both end up
  rendering the level's own string form, so they agree for every standard level. The only case in
  which they could diverge is a custom level. *T8, T9 and T10 declare no custom level, and the
  replayed events use only the standard levels `DEBUG` and `INFO`* -- which is the precise
  scope of this claim. It is deliberately not stated more broadly: this very directory contains
  unrelated custom-level fixtures, namely `log4j-customLevel.xml`, `log4j-customLevels.xml`,
  `log4j-customLevelsOverride.xml` and `log4j-customLevelsWithFilters.xml`. The `+5+` in T8's `+%5p+`
  is a separate claim from the converter's identity, and it is settled separately in the section
  immediately below.

| `+%X{transactionId}+` / `+%X{aKey}+`
| Both converters take a *single-key* branch that appends the value when the key is present and
  appends nothing when it is absent. The bridge's `properties` converter and Log4j 2's `X` converter
  are byte-identical along that branch. The distinction matters because Log4j 2's whole-map and
  multiple-key branches would instead render `{}` on empty data -- but neither fixture uses a bare
  `%X` or a multi-key form, so neither takes those branches. With the key unset, as in both captures,
  both worlds render *the empty string*.
|===

=== The `+%5p+` width, and the two claims it needs

The rewrite evidence above establishes that a width *survives* translation, because the capture group is
re-emitted -- `+%5p+` becomes `+%5v1Level+`. It does *not* establish that the width is still *in* the
translated pattern, and the two are different claims. Both are settled below, neither by guesswork and
neither by an invented event:

[WARNING]
.A five-character level cannot see a five-character field
====
`DEBUG` is exactly five characters. So are `ERROR` and `FATAL`. Rendered through a five-character
minimum field, a five-character level needs no padding, so its bytes are *identical* to those of the
same level rendered through a bare `+%p+`.

T8 is the only fixture here whose pattern carries a width, and its consumer's own emission is at
`DEBUG`. The committed capture therefore *cannot* see the width: deleting the `+5+` from the translated
pattern would leave `log4j12-perf.baseline.txt` byte for byte unchanged.
====

*Claim one -- the width is still in the translated pattern.* This is settled by observation, in the
layout-pattern row of T8's effective-configuration table above: the 2.x column is read out of the
migrated fixture's own `-Dlog4j2.debug` boot output and compared with the superseded pattern character
for character, `+%5p+` included. A width that had been dropped in translation fails that row while
rendering identical bytes, which is exactly the case the row exists to catch.

*Claim two -- the width means the same thing in both generations.* This is settled by the independent
cross-generation measurement below, which does not depend on any event this corpus replays.

[NOTE]
.Why no shorter-levelled event was added to close claim one by rendering instead
====
Adding an event at a four-character level would make the padding visible in the bytes, and it was
rejected. The superseded generation rendered exactly what T8's consumer emitted, once, at `DEBUG`; a
shorter-levelled line in this baseline would be a line *computed by this project* rather than one
*recorded from the superseded generation*, and a baseline holding computed bytes can only confirm the
reasoning that produced it. The same invented event was removed from the sibling corpus for the same
reason. Claim one is a question about the translated configuration, and it is answered with observed
configuration evidence rather than with a fabricated capture.
====

==== The same level column, measured at every standard level

T8's padding rule was measured independently of anything this corpus replays: T8's conversion pattern
was rendered for T8's own logger
and message through the *genuine Log4j 1.2.17 layout* and through Log4j 2's own `PatternLayout`, at
every standard level, and the results byte-compared. The leading `+%d+` is dropped from the probe so
that wall-clock skew between the two renders cannot defeat a byte comparison; every other token,
including the `+%5p+` under test, is the fixture's own.

[cols="1,2,2,1",options="header"]
|===
| Level | Genuine 1.2.17 level column | Log4j 2 level column | Identical

| `FATAL` | `+FATAL+` | `+FATAL+` | yes
| `ERROR` | `+ERROR+` | `+ERROR+` | yes
| *`WARN`* | `+ WARN+` -- **one leading pad space** | `+ WARN+` | *yes*
| *`INFO`* | `+ INFO+` -- **one leading pad space** | `+ INFO+` | *yes*
| `DEBUG` | `+DEBUG+` | `+DEBUG+` | yes
| `TRACE` | `+TRACE+` | `+TRACE+` | yes
|===

`WARN` and `INFO` are the only standard levels shorter than the field, and both right-align to width
five with exactly one leading space, in *both* generations. The comparison was not confined to the level
column: the whole rendered line was identical at every one of the six levels, double space before the
`-` separator included.

The unqualified `+%p+` of T9 and T10 was measured the same way, with their own logger and message, and
it *pads in neither* generation -- `WARN` and `INFO` render as four characters on both sides, and every
whole line is identical at all six levels, trailing space before the separator included. The two
families' level columns are therefore genuinely different widths by design, and each is preserved as it
stood.

*Observed in the fixtures themselves:* `DEBUG` for T8 and `INFO` for T9 and T10, in the same columns as
before the translation -- with the padding behaviour behind T8's column established by the measurement
above instead of predicted from the rewrite map, and the presence of the width in the translated pattern
established by the observed layout-pattern row rather than by a fabricated shorter-levelled capture.

=== `%c{1}` renders the full simple logger name

An all-digits option selects the abbreviator strategy documented as retaining a given number of parts
counted from the end, with one part retained. The captures accordingly show `PerformanceComparison`
and `RunLog4j1` in full, never a dot-abbreviated form.

=== The whitespace that the empty single-key rendering produces

This is the audit's most easily mistaken result, so it is stated explicitly. Because an absent
single-key context value renders as the empty string:

* *T8* renders `%c{1}`, a space, the empty string, a space, then `-`, producing *a double space
  immediately before the `-` separator*.
* *T9 and T10* render `]`, a space, the empty string, a space, then the message, producing *a double
  space between `]` and the message*; and because their pattern ends `%m %n` with a real space, every
  rendered line also carries a *significant trailing space* before the line separator.

All three are correct, byte-identical behaviour. *Trimming, collapsing or right-stripping whitespace,
in a fixture or in a baseline, is a defect,* and it is why the consuming test may not use `String.trim`
or `String.strip` on the text it compares.

=== Translations were made from the Log4j 1.x source, never from an in-repository Log4j 2 peer

This prohibition earned its keep. `log4j-perf-test/src/main/resources/log4j2-perfloc.xml`, an

== Record 4 -- Rule 6 arbitration outcomes

Where the translation could reasonably have gone two ways, baseline observed output is the
tie-breaker. Each open question is recorded below as a decision with its evidence. In every case the
normalized diff came back empty, so none of these decisions was made to *rescue* a failing
comparison; they were made to choose between alternatives the comparison could not distinguish, and
the tie-break criterion was then "reproduce genuine Log4j 1.x rather than an approximation of it".
Decision 4 is the one case where the rendered comparison was blind to the choice *and* the
effective-configuration table was not: the render could not tell the two variants apart, so the
tie-break fell to the observed effective configuration, which could.

=== Decision 1 -- T8 omits `bufferedIo` entirely

*Decision: omit the attribute.* The Log4j 1.x source declares no `BufferedIO` parameter, so there is no
value to carry across; the open question was whether to state Log4j 1.x's default explicitly.

. *Genuine Log4j 1.x was observed with buffered I/O off and an 8192-byte writer buffer.* Log4j 2's
  default buffer size is also 8192 -- it is defined as an 8 KiB encoder byte-buffer -- so leaving
  `bufferedIo` unset yields a live 8192-byte buffer, which is the same disposition.
. *Writing `bufferedIo="false"` would be worse, and provably so.* A control run adding that attribute
  to a copy of the fixture raised
  `WARN The bufferSize is set to 8192 but bufferedIo is false: false`
  and degraded the appender to per-event writes that Log4j 1.x never performed.
+
[IMPORTANT]
====
The file appender carries *two distinct* guard warnings and they must not be conflated. The one above
is the buffer-size-versus-buffering warning. The separate warning
`+Locking and buffering are mutually exclusive. No buffering will occur for {}+`
requires file locking to be switched on, which none of these fixtures does, and is *not* relevant
here. Neither warning fires for any of the three fixtures as translated.
====
. *The baseline confirms the choice.* With the attribute omitted, T8's normalized diff is *empty*.
  Buffering governs only *when* bytes reach the disk, never *what* is written, so the comparison could
  not have distinguished the two spellings -- and the omitted form is the one that matches genuine
  Log4j 1.x while emitting strictly fewer diagnostics.

=== Decision 2 -- T9 and T10 state `immediateFlush="false"` although their source never does

*This one is determined rather than arbitrated,* and it is the single most likely place for a faithful
looking translation to change behaviour silently.

Log4j 1.x *couples* buffering to flushing: its file-appender builder forces the flush flag off whenever
buffered I/O is on, in effect `if (bufferedIo) { immediateFlush = false; }`, over declared defaults of
append on, immediate flush on, buffered I/O off and an 8192-byte buffer. Log4j 2 does not couple them:
its output-stream appender builder defaults buffered I/O *on*, the buffer to the 8 KiB encoder size,
and immediate flush *on*, all independently.

The coupling is observable, not inferred. Genuine Log4j 1.x reports `immediateFlush=false` for T9 and
T10 even though neither source declares an `ImmediateFlush` parameter -- the value exists only because
`BufferedIO=true` forced it. Log4j 2 will not make that inference, so the flush setting must be stated
explicitly. *Omitting it would have turned a buffered configuration into one that flushes on every
event* -- a change in the exact disposition a benchmark fixture exists to hold still.

=== Decision 3 -- T10 states `blocking="true"` although it is also the Log4j 2 default

*Decision: state it explicitly.* Two reasons, and one observation that has to be handled carefully.

. *Genuine Log4j 1.x blocks by default.* Disassembling the published Log4j 1.2.17 artefact shows its
  asynchronous appender's no-argument constructor storing *true* into its blocking field, alongside
  128 for the buffer size and false for location capture. Genuine Log4j 1.x therefore applies
  back-pressure when the queue fills, and `blocking="true"` reproduces that.
. *The bridge does not.* Booting the unmodified Log4j 1.x fixture through the bridge shows the
  asynchronous appender built with blocking *off*, because the bridge only overwrites its flag when
  the source declares a `Blocking` parameter and this source declares none. That value is an artefact
  of the bridge, not Log4j 1.x behaviour, and reproducing it would have been the wrong target.
. *The baseline cannot arbitrate this attribute, which is why it is stated rather than left to a
  default.* Blocking governs only what happens when the queue is *full* -- wait for space, or discard.
  The queue holds 262144 events and the script emits one, so the full path is never taken; a control
  run with `blocking="false"` produced a capture byte-identical to the committed baseline. Since the
  comparison is blind to it, the conservative choice for a measurement instrument is to preserve
  back-pressure and to make that visible to a reviewer. Discarding events would also breach the
  requirement that nothing be added, removed or re-levelled.

=== Decision 4 -- root additivity is the one row whose two observed values differ

*Decision: add no attribute; record the difference and prove it inert.* Every one of T8, T9 and T10 carries
`<Root level="debug">` and nothing more, exactly as the target design specifies and exactly as mute as the
Log4j 1.x sources they translate. Log4j 1.x nevertheless reports the root's additivity as `true` while the
translated fixtures report `false`, so this is the one row in this corpus whose two observed columns do not
agree literally. Both the measurement that establishes the difference and the proof that it cannot matter
are recorded here rather than asserted.

. *What is observed.* Genuine Log4j 1.x reports the root logger's additivity as `true`. With no
  `additivity` attribute declared, the boot trace shows it unset -- `additivity="null"` in the root builder
  line -- and the built root object reports `false`. The mechanism is in Log4j 2 Core, not in these
  fixtures, and it is a deliberate asymmetry verified in source rather than inferred: the root-logger
  plugin builder declares the attribute as a *primitive* `boolean`
  (`log4j-core/src/main/java/org/apache/logging/log4j/core/config/LoggerConfig.java` L950-951,
  `@PluginBuilderAttribute private boolean additivity;`, handed to the root logger configuration unchanged
  at L1147) and returns it unconverted, so an absent attribute resolves to `false`. The builder for a
  *non-root* `<Logger>` declares the same attribute as a boxed `Boolean` (L112) and resolves an absent
  value to `true` (L140, `return additivity == null || additivity;`), and the deprecated static root
  factory likewise defaults it to `true` (L1172); only the root is affected. Omitting the attribute on a
  `<Root>` element is therefore *not* the same silence it was in the superseded generation. This is how
  every undeclared `<Root>` in the repository behaves, it is not a property of these translations, and no
  amount of reasoning about the file text would have revealed it -- only booting the fixture did.
. *Why the row is accepted rather than closed by an attribute.* The flag is *unreadable* here.
  `LoggerConfig` consults additivity in exactly two places -- the ancestor walk that decides whether caller
  location is required (L784) and the propagation step `if (additive && parent != null)` (L797) -- and both
  are guarded by a parent. The root has no parent; the boot trace reports `parent=null`. Moreover all three
  configurations declare *no logger other than the root*, so there is no additive propagation path in the
  configuration at all: no child logger exists whose events could be duplicated or dropped, and a name with
  no `<Logger>` of its own is served by the root logger configuration itself. A flag that is never read
  cannot change behaviour, and that -- not the tidiness of the row -- is what discharges it.
. *A control run proves the two variants are byte-identical.* Every fixture was replayed with the attribute
  stated and again with it absent. The built root reports `true` under the first and `false` under the
  second, and *every other observable is unchanged*: the raw captures are identical under the two variants
  (T8 72 bytes over one line, T9 43 bytes, T10 43 bytes), every normalized diff between the two variants is
  empty, and all three captures reproduce their committed baselines byte for byte. Booting with
  `-Dlog4j2.debug` emits no `WARN`, `ERROR` or `FATAL` status line under either variant -- which also
  confirms that `additivity` is a recognised attribute of the root element rather than something tolerated
  in silence. The seven fixtures of the peer corpus were measured the same way with the same result, so the
  two corpora are treated identically.
. *Why stating `additivity="true"` was rejected.* An intermediate state of this corpus did state it, and it
  did make the row agree literally. It was removed because it puts an attribute in the translated file that
  has *no counterpart in the file being translated*: the Log4j 1.x sources declare no additivity, and a
  corpus whose purpose is to show that a translation adds nothing cannot itself add something. The
  comparison with `blocking="true"` in Decision 3 does not rescue it, either -- that attribute states a
  Log4j 2 default in order to make a *preserved behaviour* visible, whereas this one would state a value in
  order to make a *reported flag* agree, and the flag is the one thing here with no behaviour to preserve.
. *What a reviewer should take from the row.* All three naive readings of it are wrong. "`The flag differs,
  therefore the migration changed additivity`" is wrong: nothing consults the flag. "`The default is true,
  therefore there is nothing to check`" is wrong, and was the actual trap, because for the root logger that
  default is *not* `true`. And "`state the attribute so the row agrees`" is wrong too, because it buys a
  literal match with an invented attribute. The row stands as the corpus's one named exception, in the same
  way the normalized `%L` token stands as its one tolerated rendered-output difference: declared, measured,
  and bounded.

=== A note on the bridge as a reference point

One further observation is recorded because it vindicates two of the decisions above and would
otherwise look like an inconsistency. For T8, the bridge reports `immediateFlush=true` -- it does not
honour the source's explicitly declared flush parameter, and capitalising that parameter's name does
not change the outcome -- whereas genuine Log4j 1.x reports `false`. The bridge is therefore an
*approximation* of Log4j 1.x in two of the places this corpus touches: T8's flush flag and T10's
blocking flag. In both, the translated fixture matches *genuine* Log4j 1.x rather than the bridge, and
in both the rendered output is identical regardless. That is the correct target: the migration is away
from Log4j 1.x, not away from the bridge's rendition of it.
