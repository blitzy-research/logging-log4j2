# =============================================================================
# Log4j 1.x -> Log4j 2 MIGRATION PARITY CORPUS -- CUSTOM-COMPONENT COUNT
# BASELINE
# =============================================================================
#
# PURPOSE
# -------
# This file records the pre-migration event counts of the ONE custom logging
# component the migration removes, and it is the sole oracle for that
# component's parity.
#
# The removed component was a counting no-op appender: it rendered nothing, it
# wrote nowhere, and it simply incremented a counter once per appended event.
# The two configurations that used it therefore produce NO rendered text, so
# there is nothing here for the four-token normaliser that governs the five
# rendered-output baselines beside this file. For a counting no-op appender the
# COUNT is the observable contract, so count identity IS output identity. That
# is why this component's comparison test asserts on a number rather than on
# lines of text, why the number is recorded here rather than as a capture file,
# and why a rendered-text comparison must never be substituted for it.
#
# Migration policy requires one comparison test per custom logging component,
# and such a test needs a recorded pre-migration count to compare against.
# Captured baseline output is the tie-breaker for every behavioural ambiguity,
# which is what makes the two numbers below authoritative. This corpus is
# mandatory companion evidence for the change, not optional extra work.
#
# PROVENANCE OF THE CONSTRAINTS RECORDED BELOW
# --------------------------------------------
# No separate on-disk user rules document exists for this project; the rules
# source reports that none was provided. Nothing here is therefore invented,
# and that absence is not treated as licence to lower the bar. Every constraint
# recorded below is carried from the migration plan governing this change.
#
# Both numbers were OBSERVED BY EXECUTION rather than argued for, and every
# anchor was identified by its content signature, never by a line number,
# because line numbers drift. Where the plan's prose and the sources
# disagreed, THE SOURCES WON.
#
# -----------------------------------------------------------------------------
# FILE FORMAT
# -----------------------------------------------------------------------------
# Encoding UTF-8, no byte-order mark. Line endings LF, which the repository
# enforces for every text file. No trailing whitespace on any line. The file
# ends with exactly one LF.
#
# There is deliberately NO LICENCE HEADER. A header would be indistinguishable
# from payload and would force every consumer to implement header skipping, so
# the payload is kept pure. An inherited src/test/resources directory exclusion
# keeps the release-audit header check off this file, and that exemption was
# confirmed against an actual audit run rather than assumed. If an audit run
# ever does flag a file here, the remedy is a module-level audit exclusion
# agreed with the owner of the module build file -- never a header inside the
# payload. The source formatter does not reach this file either, because its
# scope is Java sources only, so the layout below is maintained by hand.
#
# The file is line-oriented:
#
#   * blank lines are permitted for readability and MUST be ignored;
#   * a line whose first non-whitespace character is '#' is a comment and MUST
#     be ignored;
#   * every other line is a data line.
#
# Data-line grammar -- with NO spaces around the equals sign:
#
#     <configId>=<count>
#
#   <configId>  T6 or T7. Selects the configuration whose count is recorded.
#               These are the identifiers used by the fixed event script that
#               sits beside this file.
#   <count>     a non-negative decimal integer. No sign, no digit separator,
#               no unit and no suffix.
#
# Equivalent validating expression for a data line:
#
#     ^T[67]=[0-9]+$
#
# There are EXACTLY TWO data lines, T6 first and T7 second.
#
# STRICT DETERMINISM. Each number is the count for ONE SINGLE REPLAY of the
# fixed event script -- it is not a benchmark result. It has no timing
# dependence, no thread-count dependence, and no relationship whatsoever to any
# benchmark iteration, fork or warm-up setting. Four independent runs of each
# configuration, each in a fresh JVM, produced identical numbers.
#
# -----------------------------------------------------------------------------
# THE TWO CONFIGURATIONS
# -----------------------------------------------------------------------------
#   id  classpath resource                             root   observable
#   --  ---------------------------------------------  -----  -----------------
#   T6  /perf-log4j12-async-noOpAppender.xml           debug  count, async
#   T7  /perf-log4j12-async-location-noOpAppender.xml  debug  count, async,
#                                                             caller location
#
# Both keep their existing file name and their existing classpath location; the
# migration changes only the schema inside each file, so nothing that selects
# either of them by resource name had to change. Both wrap the counting
# appender in an asynchronous appender, retaining the original NON-DEFAULT
# buffer size of 262144 and blocking back-pressure, and T7 additionally retains
# caller-location capture. Neither writes a destination file, so the fresh-file
# contract that applies to the rendered-output baselines does not apply here --
# but the queue-drain requirement below absolutely does.
#
# -----------------------------------------------------------------------------
# HOW THESE NUMBERS WERE CAPTURED
# -----------------------------------------------------------------------------
# The removed component exposed its counter as a PUBLIC FIELD holding an atomic
# long, incremented exactly once per appended event. The baseline was therefore
# read as
#
#     appender.count.get()
#
# -- A FIELD READ, NOT A GETTER CALL. The replacement plugin that Core already
# ships exposes the same counter as an instance METHOD, getCount(). The two
# generations are thus deliberately asymmetric in API SHAPE while being
# identical in counting semantics: one increment per appended event, in both.
#
# That asymmetry is resolved entirely on the reading side, by retrieving the
# appender BY NAME. No adapter, wrapper, shim or field-exposing subclass exists
# anywhere in this change to bridge it, and no dependency was added to satisfy
# this criterion -- the replacement plugin was already on the module's compile
# classpath. The asymmetry, and the removal of NoOpLog4jAppender itself, are
# recorded as a documented test-infrastructure adaptation in the
# effective-configuration tables beside this file.
#
# Capture procedure, performed once per configuration in a fresh JVM:
#
#   1. boot the ORIGINAL Log4j 1.x configuration for that id;
#   2. retrieve the counting appender BY NAME -- the root logger's appender
#      named ASYNC, then that appender's nested appender named NoOp -- and hold
#      the reference, because shutting the hierarchy down detaches appenders;
#   3. replay ONE fresh pass of the fixed event script, emitting only that
#      id's lines, in file order;
#   4. DRAIN the queue by shutting the context down, which stops the
#      asynchronous appender and empties its buffer;
#   5. only THEN read the counter.
#
# ** THE DRAIN IN STEP 4 IS LOAD-BEARING, NOT DECORATIVE. ** Both
# configurations increment the counter on the asynchronous appender's own
# background thread, so a read taken before the queue has drained under-counts.
# This was demonstrated rather than assumed: an undrained read of T7 returned 0
# on every attempt, against its drained value of 1. An under-count is NEVER to
# be "fixed" by sleeping and hoping, and NEVER by lowering the recorded number.
#
# Environment: the migration base commit, on the project's documented JDK 17
# build baseline, with the Log4j 1.x classpath still present and BEFORE any
# dependency removal. The transient harness that drove the 1.x emissions is not
# part of this change and was not committed; only the numbers below were.
#
# -----------------------------------------------------------------------------
# ** CAPTURE ORDERING -- THE DIRECTION MUST NOT BE CONFLATED **
# -----------------------------------------------------------------------------
# BEFORE: this baseline is captured against the removed 1.x component and the
#         ORIGINAL 1.x configurations, while the 1.x classpath is still
#         present and before any dependency removal. Once the migration's
#         main-source change lands, the component and its public counter field
#         no longer exist and THE CAPTURE CANNOT BE REDONE.
#
# AFTER:  the comparison runs against the migrated Log4j 2 configurations and
#         the replacement plugin, and is asserted by this component's
#         comparison test.
#
# The comparison test must therefore read the migrated count as
#
#     ctx.getConfiguration().<CountingNoOpAppender>getAppender("NoOp").getCount()
#
# -- the appender retrieved BY NAME, NoOp as referenced from ASYNC -- replay the
# same single pass of the same script, and assert EXACT EQUALITY against the
# numbers below. Acceptance is exact equality, nothing weaker. A MISMATCH IS A
# DEFECT IN THE MIGRATION AND IS FIXED IN THE MIGRATION; IT IS NEVER A REASON
# TO ADJUST THE RECORDED COUNTS.
#
# -----------------------------------------------------------------------------
# WHY THE NUMBERS ARE TWELVE AND ONE
# -----------------------------------------------------------------------------
# ** TWELVE FOR T6, NOT ELEVEN. ** The migration plan's prose counts eleven
# because it counted only the concatenating benchmark arms. The benchmark that
# consumes T6, AsyncAppenderLog4j1Benchmark, declares TWELVE: one simple arm
# logging a shared sixteen-character constant, then eleven arms concatenating
# one to eleven parameters. Those arguments STAY CONCATENATED -- no argument is
# converted to placeholder parameterisation anywhere in this migration, because
# a parameterised arm already exists as a separate benchmark class and
# converting would destroy the very comparison the harness exists to make --
# and that is precisely what keeps the arm count at twelve.
#
# T7's benchmark, AsyncAppenderLog4j1LocationBenchmark, declares exactly ONE
# arm, logging the same shared constant. Caller-location capture changes the
# COST of an event, not the NUMBER of events, so T7's count is one.
#
# Counting the benchmark annotation with a naive substring search is
# misleading: it also matches the benchmark-mode annotation carried by every
# arm, and so reports double. The counts here were established by matching the
# annotation on its own line, by pairing it against the benchmark-mode
# annotation, and by counting emission statements. All three agree at twelve
# and one, so no correction to the recorded numbers is owed.
#
# Four independent corroborations, all agreeing:
#
#   * the observed capture itself -- 12 events replayed counted 12, and 1
#     event replayed counted 1, with the counter starting from 0 in both;
#   * the fixed event script beside this file carries 12 T6 lines and 1 T7
#     line;
#   * the benchmark sources declare 12 and 1 arms, and 12 and 1 emissions;
#   * the fixed event script's own cross-reference states these very numbers.
#
# =============================================================================
# THE BASELINE
# =============================================================================
T6=12
T7=1
