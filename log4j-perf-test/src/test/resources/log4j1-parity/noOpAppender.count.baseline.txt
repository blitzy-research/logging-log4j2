# =============================================================================
# CUSTOM-COMPONENT COUNT BASELINE
# =============================================================================
# Both configurations below wire a counting no-op appender, which renders nothing
# and writes nowhere, so its COUNT is the whole of its observable contract: for
# this component, count identity is output identity.
#
#   id  configuration                                  observable
#   --  ---------------------------------------------  ------------------------
#   T6  perf-log4j12-async-noOpAppender.xml            count, async
#   T7  perf-log4j12-async-location-noOpAppender.xml   count, async, location
#
# PROVENANCE. Each number was read from a public field holding an atomic long,
# incremented once per appended event, as `appender.count.get()` -- a field read
# rather than an accessor call. It is the count for ONE replay of that id's lines
# of the event script beside this file, in file order, with no timing,
# thread-count, iteration, fork or warm-up dependence; replays in fresh virtual
# machines reproduce it. The capture was taken against the original
# configurations, before they were translated, and CANNOT BE REDONE, because the
# counter field it was read from no longer exists. The transient harness that
# drove those emissions is not committed; only the numbers are.
#
# NOT THE SOLE ORACLE. Before comparing a recorded number with what the appender
# received, the consuming gate holds it to the number of records the event script
# replays into the same fixture -- 12 for T6, 1 for T7 -- and to the exact bytes
# of each payload record: every record must match ^(T[67])=([0-9]+)$ in full, so
# one carrying a sign, separator, unit or surrounding space is rejected rather
# than read as valid, and the records must be T6 then T7, in that order, with no
# repetition, rename or addition. Comment and blank lines are dropped before that
# check, which is what lets this provenance travel with the numbers without
# loosening the grammar. An edit to either artefact alone therefore fails, and a
# number quietly lowered to accommodate an undercount cannot pass.
#
# HOW THE APPENDER IS RESOLVED. The plugin these fixtures wire exposes the same
# counter as an instance method rather than a field: identical counting
# semantics, different API shape. That asymmetry is resolved entirely on the
# reading side -- no adapter, wrapper, shim or field-exposing subclass exists,
# and no dependency was added, because the plugin is already on this module's
# compile classpath. The gate resolves the appender BY NAME (NoOp, as referenced
# from ASYNC) from the running configuration, which yields an Appender; it then
# asserts the concrete type and casts before reading the counter, so a fixture
# that bound that name to some other appender reports what it bound instead of
# failing with a bare cast error.
#
# ORDERING, WHICH IS LOAD-BEARING. Resolve the appender while the context still
# runs, replay the script, then STOP the context -- which is what stops the
# asynchronous wrapper and drains its buffer -- and only THEN read the counter.
# Both configurations increment on the wrapper's background thread, so a read
# taken before the drain under-counts: an undrained read of T7 observes 0 against
# its drained value of 1, on every attempt. An under-count is never resolved by
# sleeping and hoping, and never by lowering a recorded number. A mismatch is a
# defect in the translated configuration and is fixed there.
#
# THE PAYLOAD. Exactly two data lines, T6 first and T7 second, each matching
# ^T[67]=[0-9]+$ with no space around the equals sign. Everything above is
# commentary: the consuming gate skips comment and blank lines and validates
# every payload line strictly, so this prose can be read by a person without
# loosening the grammar.
T6=12
T7=1
